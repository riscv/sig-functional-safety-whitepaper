[#sec:redundancy]
## Redundancy

[#sec:redundancy:safety]
### Safety needs


A safe system is is one in which faults are detected, contained, or
mitigated such that the resulting risk remains within acceptable limits.
These faults can be transient or permanent. Transient faults are one-off
events after which the affected component returns to normal operation,
unless the fault has already caused a failure or propagated to another
component. Permanent faults persist and typically require intervention
to restore the affected component to normal operation.

Faults can have an internal (e.g., bug, device aging) or external (e.g., high
energy particle, electrostatic discharge, excessive heat) origin.

A failure that has a single root cause but affects more than one component is
known as a common-cause failure.

Redundancy is the partial or complete replication of components or information to detect
and/or correct faults.

Redundancy can be introduced into the system on different levels:

* Hardware redundancy is achieved by replicating physical resources, for example
including multiple processors or whole SoCs, or replicating elements such as
memory or sensors.
* Software redundancy means a task is implemented in software in multiple
different ways and each version is executed.
* Information redundancy can help detect or correct data corruption by storing
additional data, such as an error detecting and correcting code.
* Time redundancy is brought about by executing the same task on the same
processor multiple times.

In all of these cases, execution on a redundant system is followed by a decision step, in
which the output from each redundant execution (or the redundant information in
the case of information redundancy), is compared.
If the output differs, then a failure has occurred in one or more executions and
an error can be reported.
If the redundancy is implemented by using more than two replicas, the system can
continue running when a majority of the replicas produce the same output.

Different types of redundancy are used to detect and/or prevent different
categories of failures.
Hardware redundancy is used to handle failures of hardware elements. Software
redundancy is used to mitigate defects introduced during the development phase.
Information redundancy protects the system against data corruption. Time
redundancy is used to detect or mitigate transient faults.
Note that HW-SW co-engineering methods also exist, for which this strict
classification might not be fully correct. However, these descriptions provide a
useful fundemental understanding.

Redundancy can mitigate both random-permanent and transient faults, of both
internal and external origin. Diverse redundancy also supports claims with
respect to systematic faults.

Both software redundancy and time redundancy are typically managed by purely
software means without explicit hardware support.
Hence, they are excluded from the discussion in the remainder of this chapter.

[#sec:redundancy:features]
#### Features

##### Information Redundancy

Apart from full replication, information redundancy can be achieved by
techniques such as error detection and correction codes (EDC/ECC) in memory.

##### Hardware Redundancy

Redundancy can be characterized by its level of diversity.
If, for example, multiple identical hardware elements are integrated without
modification, the diversity is low.
Diversity can be increased by triggering software execution on each system
with an offset of a number of clock cycles. Additional diversity can be
achieved by incorporating elements of differing design, differing ISAs, or even
differing manufacturers.

Diverse redundancy is particularly useful for mitigating common-cause failures.
When a fault affects redundant, diverse components, the resulting errors are less
likely to be identical, increasing the likelihood that the errors will be detected
and the resulting failure avoided.

The level of diversity required by a system depends on the target safety level,
as well as the domain.
For example, executing a process with a clock cycle offset on identical
processors might be sufficient for systems in the automotive domain, but not in
avionics.

Redundancy can be further characterized by its cardinality.
In general, redundancy can be characterized as an M-out-of-N (MooN) system,
where N is the total number of redundant elements and M is the minimum number of
elements that must remain functional for the system as a whole to remain functional.

By including two redundant components (1oo2) in the system, also known as dual
modular redundancy, individual faults can be detected. However, when the output of
the two components differs, the system cannot decide where the fault occurred
and hence which result is the correct one.
To allow the system to continue executing in such a case and therefore correct the
fault, the component must be included in triplicate (2oo3, triple modular redundancy),
or in a greater number of instances (e.g., 3oo5).

The comparison module can then decide by majority voting which output is the
right one and which component has failed.

NOTE: This implies that the comparison module has to fulfill high-integrity
requirements with respect to absence of systematic faults.

Redundant hardware can be used either as a fallback component that remains idle
until the primary component fails, assuming full replication, or during normal
execution in parallel with the primary component. The latter approach can be used
to detect or correct faults during operation. Some models also support partial
replication.

In the former case, the fallback system typically provides a subset of the
functionality of the primary system, allowing the system to operate in a degraded
state. It is used only for a limited period, until the primary system is restored
or the system can be transitioned to a safe state.

Hardware redundancy is often implemented by replicating a processor and
comparing the output of the computation at the end of a task's execution.
However, if the task is initiated in the same, or offset, clock cycle on
identical processors and the state of the execution is compared at regular
intervals, or steps, it is referred to as lockstep computing.
The definition of a step can vary. For example, a step can consist of a fixed
number of clock cycles or be delineated by specific events, such as writes to
memory, interrupts, or other off-core events.

For lockstep computing, an additional comparison module is required to perform
regular checks of the state of the systems.
Such module must also be intrinsically redundant or tolerant to the relevant
fault modes that affect the redundant components.




Time redundancy can additionally be introduced into lockstep execution by
starting the redundant tasks in different clock cycles, with one task offset
from the other by a specified number of cycles.
This method avoids common-cause failures due to transient faults.

Examples of lock-step include dual core lock-step (DCLS), as an implementation
of 1oo2, and triple core lock-step (TCLS), which is 2oo3.
The cores can be initiated in the same clock cycle or offset.

In the context of RISC-V, there might be additional levels of diversity of
redundancy to consider.
Since RISC-V is an open instruction set architecture (ISA), several different
implementations exist by different independent providers.
Different implementations can be combined in a system to provide a level of
diverse (microarchitectural) redundancy.
However, while this kind of redundancy will detect (and possibly correct)
failures due to the implementation, it assumes that the ISA itself does not 
contain any faults.

Traditionally, heterogeneous systems imply diversity of ISAs. ISA diversity
has the added benefit of introducing a certain degree of diversity in the
software development process as well, as different tools, such as compilers, are
required to program the processor.
When you use different RISC-V implementations, it is therefore worth
considering the use of different compiler implementations for each replicated
processor, unless other measures, such as qualification kits, exist.

Whether the level of redundancy achieved by combining different RISC-V
implementations, potentially with different toolchains, is sufficient depends
on the safety level and domain of the system.

[#sec:redundancy:safety:level]
#### Level

Both the core and the whole SoC can be replicated for redundancy purposes.

[#sec:redundancy:safety:importance]
#### Importance

While most safety standards do not explicitly require redundancy, redundancy
is one of the key techniques used to achieve the levels of fault tolerance
required for higher safety levels. This can be seen in functional safety standards
such as ISO 26262 cite:[iso26262:2018] and IEC 61508 cite:[iec16508-1:2010].

In the context of ISO 26262, redundancy is integral to
"`ASIL tailoring`" i.e., the decomposition of safety requirements to redundant
architectural elements,
whereby, if the absence of dependent failures can be demonstrated, the ASIL
allocated to the redundant elements can be reduced.

Similarly, IEC 61508-2:2010 cite:[iec16508-2:2010] provides guidance for the
maximum diagnostics coverage of a variety of redundancy techniques, and
IEC 61508-6:2010 cite:[iec16508-6:2010] Annex B provides guidance for evaluating
probabilities of hardware failure that includes various redundant voting
schemas.
In addition, IEC 61508-2:2010 Annex E defines normative requirements for
"`__Special architecture requirements for digital integrated circuits (ICs) with
on-chip redundancy__`" to avoid common cause failures for ICs that share the
same substrate.

[#sec:redundancy:safety:justification]
#### Justification

Redundancy is often the only mechanism to detect errors and remain operational
to the extent required by systems with high safety levels.

Basic redundancy can improve integrity by providing a method for error detection
and eventually correction, although both can by accompanied by degradation of the main
functionality.
If the redundancy is further increased, the system can also show improved fault
tolerance and reliability, since single faults are corrected, as long as
they do not lead to common cause failures. Mitigating common-cause failures generally
requires diversity in addition to redundancy.
In a primary-backup setup, availability can increase because the backup component can be available
even if the primary component has failed.

ISO 26262:5 cite:[iso26262-5:2018] mentions redundancy as a safety mechanism,
with typical diagnostic coverage considered achievable described as "`High`".

ISO 26262:11 cite:[iso26262-11:2018] also specifically mentions diverse
redundancy as a tool to reduce risk of hardware failures when using IP with
limited documentation and insufficient historic (aka "`proven in use`") data.

Error detection and correction modes are described in
ISO 26262:11 cite:[iso26262-11:2018] as a technique to detect failures in
memory.

[#sec:redundancy:rv]
### RISC-V solutions

Because redundancy is intended to be transparent to the software, no
RISC-V-specific features have been defined specifically for redundancy.

[#sec:redundancy:recom]
### Recommendations

Redundancy is intended to be completely transparent, hence no changes to the ISA
are required.
