[#sec:pmc]
## Performance counters

[#sec:pmc:safety]
### Safety needs

Performance counters are used to monitor and analyse safety-critical
solutions in systems which include sources of indeterminism.
They were primarily designed for application profiling and performance tuning,
but the ability to observe the behaviour of the hardware as an application is
executed is valuable for development and runtime monitoring of safety-critical
systems.

[#sec:pmc:safety:features]
#### Features

Performance Counters, frequently referred as PMCs for Performance Monitoring
Counters, count events occurring in a core or processor.
The exact nature of events to count depends on the actual core/processor
architecture, but typically they count events as:
Cache and TLB usage (hit/miss), number of executed instructions and clock
cycles, stalled cycles, Load/Store accesses, branch prediction statistics,
and number of exceptions raised.

Next, in <<tab:pmc:pmc-types>> we provide a detailed breakdown across the main
performance counter types, along with some details on the information that would
be needed to ease verification and validation of safety-related systems, as well
as for the implementation of safety measures.
The table also indicates the source, core or another SoC IP, the event usually
comes.

In addition to performance counters, a programmable threshold feature
should be provided for each performance counter.
Programmable thresholds enable actions to be associated with a counter
whenever it exceeds its threshold.
For example, a cache-miss counter or pipeline-flush counter can have
an associated programmable threshold. When the counter exceeds this
threshold, an action (e.g., raising an interrupt) can be triggered.
This threshold feature can often also be implemented as an overflow
feature if the counters can be configured to overflow at a programmable value.
For example, software can use this functionality to enforce quotas.
Note that resource allocation in safety-critical systems may also require additional
hardware support.

Another feature useful for safety analysis and control is programmable filtering
of performance counters, where applicable.
Following the cache-miss counter example, filtering allows the counter to be
updated only for cache misses to specific address ranges.
However, the filtering capabilities provided depend heavily on the semantics
of the event, such as the address range or event source.

Quota and filtering features can support software control mechanisms in
mixed-criticality systems to help ensure the safety of critical applications.
For example, a software control mechanism can use both features to monitor
non-critical applications by filtering events to include only addresses mapped
by those applications. It can then raise an interrupt to stop their execution
when a quota is exceeded, such as a specified number of cache misses.

Likewise, when designing a system, these features can help debug specific
applications by filtering relevant events and raising signals or alarms when
a specified threshold is reached.

[#sec:pmc:safety:level]
#### Level

Performance Counters in the context of safety are needed at both the
SoC and core levels.
The level or scope at which a counter is deployed depends on the location
of the component being monitored.
For instance, instruction counts, branch-related statistics, and similar
events generally occur at the core level and are therefore appropriately
monitored at that level. Other events, such as those related to memory and
peripheral controllers, must clearly be monitored at the SoC level.
Some events, such as those related to shared caches, may fall into either category,
depending on the specific implementation. For example, a shared cache may be a
standalone component and therefore belong to the SoC level, or it may be part of a
cluster of cores such that the cores and shared cache cannot be deployed separately.
In the latter case, the performance counters can be considered to be at the core level.

Hypervisors, OSes, and RTOSes can implement additional counters at the software level,
either to complement hardware counters or as an alternative when hardware counters are
not available for some event types.
Software-based counters are appropriate for monitoring software-visible events, such as
those related to peripherals, DMA, and some memories (e.g., certain flash memories). Such
components may only be accessible through specific hypervisor, OS, or RTOS services, allowing
those software layers to implement counters that monitor activities related to those devices,
such as access counts and the amount of data transferred. Other software-visible events, such as
interrupts and exceptions, can also be monitored using software counters implemented in the
hypervisor, OS, or RTOS.

[#sec:pmc:safety:importance]
#### Importance

Performance counters are important for timing-sensitive applications that are
implemented on architectures where timing interference can occur between
processes, cores, or other sources of indeterminism.

Performance counters can be used at any criticality level.
The need for them generally increases with the criticality of the functionality,
although it also depends on the characteristics of the hardware and software platform.

For instance, if the SoC provides a high degree of isolation across cores such
that interference is low and limited by construction, or is fully controllable
through software, performance counters for monitoring interference or breaking down
activity across cores may not be required.
In this case, analyses could be performed in isolation, with estimates developed based
on available access counters, without implementing safety measures that require
performance counters. Overruns during operation would then not depend on how
hardware resources are shared.

Therefore, there is no _one-size-fits-all_ solution in terms of performance
counters. In general, however, a greater number of performance counters, more detailed
breakdowns, and more per-core information can make an SoC easier to
integrate into safety-relevant systems by reducing the costs associated with verification,
validation, and implementation of safety measures.

Along with providing performance counters, it is important to document them properly in
the corresponding technical reference manuals.
Counters are often described only by their names or in one-line descriptions.
These descriptions introduce uncertainty, and even when a performance counter could be useful,
it may ultimately be ignored because there is insufficient information or evidence that it
provides the required information.

It is therefore important to provide detailed documentation describing precisely what
each performance counter measures.

[#sec:pmc:safety:justification]
#### Justification

This section first describes why performance counters are needed in safety-related systems
and then reviews specific use cases through several examples.

[#sec:pmc:safety:justification:standards]
##### Traceability to standards

Performance Counters can be used as a basis for meeting safety requirements
related to a variety of safety needs, such as "freedom from interference"
(ISO 26262 cite:[iso26262:2018]), "resource usage tests" (ISO 26262
cite:[iso26262:2018]), and "interference channel characterization"
(CAST 32-A cite:[cast32:2016]), as well as processes related to timing estimation,
critical configuration validation, and random hardware fault management.

safety-relevant systems, their use can be identified in at least three different
phases of the product lifecycle:

Putting performance counters in the context of the product life-cycle of
safety-relevant systems, we foresee their need in at least three different
phases of the product life-cycle:

* During verification, performance counters are needed for estimation purposes,
  such as estimating timing, memory usage, peripheral usage, and other resource
  requirements.
* During validation, test campaigns are conducted, and performance counters are
  typically used to assess actual resource usage against estimates and to diagnose
  misbehavior, since counters can provide detailed information about its source.
* At run-time, the integrity or assurance level of the functionality determines the
  safety measures needed as part of the system architecture.
  Some of these safety measures may include monitoring, quota, and/or diagnostic
  capabilities to proactively prevent failures or to respond to specific events by
  taking corrective actions promptly and precisely (e.g., degrading the system by
  stopping the offending task).

In all those cases, evidence obtained from performance counters can be used to
feed certification documentation.

[#sec:pmc:safety:justification:uses]
##### Specific uses of performance counters

Without being exhaustive, this section identifies several uses of
performance counters in the context of safety-relevant systems.

[#sec:pmc:safety:justification:uses:wcet]
###### [.h4-example-heading]#Example 1: WCET estimation#

Performance counters can be used for measurement-based timing analysis or to
provide input data, such as latency measurements, for static timing analysis.
In particular, performance counters can be used to measure the number of
accesses to each shared resource and the maximum latency experienced by each
resource under stressful scenarios. These measurements can then be used to
estimate the execution time assuming that all accesses experience the
corresponding worst-case latencies.

In the context of automotive systems, it is also common to optimize the
timing behaviour of critical tasks without performing a formal WCET
estimation process, as may be required in other domains such as avionics.
In such cases, performance counters can provide input to timing models that
are used to determine task scheduling that minimizes the overall execution
time, based on the model.

[#sec:pmc:safety:justification:uses:valid]
###### [.h4-example-heading]#Example 2: Resource usage validation and diagnostics#

Performance counters can be used to measure accesses to different resources
(e.g., peripheral devices and DRAM), as well as the amount of data transferred during the
validation phase of a subsystem, to verify that specific bandwidth bounds are not
exceeded.

Another example is assessing whether timing deadlines are exceeded.
If a deadline is exceeded, performance counters can provide a precise and detailed
snapshot of resource usage for the task experiencing the overrun, as well as for
potentially offending tasks.
Such information can enable rapid diagnosis of the source of the overrun.

Performance counters can also be used when no overrun has occurred to predict potential
future overruns as further integration takes place. For example, they can reveal whether
specific resources are already highly stressed and, therefore, whether integrating additional
applications could lead to resource overutilization.

[#sec:pmc:safety:justification:uses:monitoring]
###### [.h4-example-heading]#Example 3: Resource usage monitoring and diagnostics#

As with the previous example, performance counters can be used during operation, analogously
to the validation process, but to implement safety measures.
For instance, some counters can be read periodically to detect whether a task is abusing
a resource or exhibiting other types of misbehavior that may affect other tasks.

Alternatively, instead of continuously monitoring these counters, tasks can be allowed to
run until a failure to meet a given deadline or complete a sufficient number of jobs within
a given time period occurs. The performance monitoring counters can then be used to diagnose
the cause of the excessive execution time. Diagnostic information can be used not only for
immediate decisions but also to track historical behavior. For instance, if a task experiences
overruns too frequently, the system can switch to a different precomputed task schedule.

[#sec:pmc:safety:justification:uses:quota]
###### [.h4-example-heading]#Example 4: Quota allocation#

If performance counters support programmable quotas (e.g., a maximum number of
accesses to, or amount of data transferred through, a specific resource), safety
measures can be implemented based on those quotas.

For example, a maximum number of DRAM accesses can be defined for a task over a
specific period to limit the amount of interference that the task can cause to other tasks.
Upon reaching the limit, quota-related counters can raise an interrupt, allowing the hypervisor,
OS, or RTOS to perform an appropriate corrective action. For instance, the system could drop a
specific job of the task if its continued execution may affect more critical tasks, or drop other
tasks if the task is highly critical and has become more vulnerable to interference.

[#sec:pmc:safety:justification:uses:faults]
###### [.h4-example-heading]#Example 5: management of random hardware faults#

Performance counters related to detected and/or corrected errors can be used to detect
intermittent and permanent faults.

For instance, SECDED codes deployed with some DRAM memories can detect and correct transient
faults caused by, for example, particle strikes. Performance counters can also track whether such
errors occur too frequently or are too concentrated in a specific component (e.g., a DRAM DIMM).

If the number of errors exceeds predefined thresholds, performance counters can be used to trigger
corrective actions, such as replacing a component (e.g., a DIMM) or performing a hardware repair
(e.g., replacing a cache line with a spare one). Such actions can prevent components from becoming
unprotected when error-correction capabilities are being used to correct permanent or intermittent
errors, which can otherwise leave transient faults uncorrectable.

[#sec:pmc:safety:justification:uses:contrib]
##### Contribution to safety properties

This section refers to the safety properties presented in the main chapter of
this white paper and how performance counters address them:

* Availability: Performance counters can be used to monitor or control the
  correct real-time behavior of the system, the bounded impact of interference
  channels, the correct usage of resources, and so on.
* Reliability: Performance counters can be used to detect or control the
  over-consumption of resources that could provoke an excessive thermal
  dissipation.
  In addition, they can be used to measure the occurrences of errors.
* Observability: Performance counters provide observation capabilities that
  can be used during software and hardware development and at run-time.

[#sec:pmc:rv]
### RISC-V solutions

The RISC-V Privileged ISA Specification cite:[rv-priv-spec:2024] Section 3.1.10
outlines a basic hardware performance counters facility for M-Mode.
In particular, the following counters are included:

* Machine cycle counter (`mcycle`) CSR: Counts the number of clock cycles
  executed by the processor core on which the hart is running.
* Machine instruction retired counter (`minstret`) CSR: Counts the number of
  instructions that the hart has retired.
* Machine performance monitoring counters (`mhpmcounter3` - `mhpmcounter31`):
  Counts platform-specific events. An additional set of Event Selector CSRs
  (`mhpmevent3`– `mhpmevent31`) controls which specific event causes the corresponding
  counter to increment.

RISC-V performance counters are 64 bits wide. In RV32 processors, they are accessed
through two 32-bit CSRs containing the least-significant and most-significant halves
of each counter.

The RISC-V Unprivileged ISA Specification cite:[rv-unpriv-spec:2024] Chapter 8 defines,
through the [.extension]#Zicntr# and [.extension]#Zihpm# extensions, an analogous facility
for unprivileged hardware performance counters, including the Cycle Counter (`cycle`) CSR,
the Instruction Retired Counter (`instret`) CSR, and 29 additional Performance Monitoring
Counters (`hpmcounter3`–`hpmcounter31`).

The RISC-V Privileged ISA Specification cite:[rv-priv-spec:2024] Section 10.1.4 also addresses
the Supervisor Software case, specifying that it uses the same hardware performance monitoring
facility as user-mode software.

Additional CSRs are defined to provide control over counter activation (Machine Counter-Inhibit
CSR, RISC-V Privileged ISA Specification cite:[rv-priv-spec:2024] Section 3.1.12) and the availability
of hardware performance-monitoring counters to the next-lower privileged mode (Counter-Enable Register CSR,
RISC-V Privileged ISA Specification cite:[rv-priv-spec:2024] Sections 3.1.11 and 10.1.15, for machine and
supervisor modes, respectively).

The RISC-V Privileged ISA Specification cite:[rv-priv-spec:2024] Chapter 17 defines the [.extension]#Sscofpmf#
extension, which provides performance-counter overflow and mode-filtering capabilities for machine and supervisor
modes. The overflow capability allows the implementation of quotas, as described in the Features section of this
chapter (<[sec:pmc:safety:features](sec:pmc:safety:features)>), while the mode-filtering capabilities partially
address the filtering capabilities identified in the same section, but are limited to execution modes. Note that
the overflow capability does not apply to the mandatory `cycle` and `instret` counters.

[#sec:pmc:recom]
### Recommendations

[#sec:pmc:recom:safety]
#### Safety usage

Version 1.11 of the RISC-V Privileged Architecture Specification introduced the
Machine Counter-Inhibit (`mcountinhibit`) CSR.

While this register allows counters to be stopped to reduce energy consumption or
mitigate certain side-channel security attacks, doing so may violate safety requirements
or assumptions that depend on a counter remaining continuously active.

A system designer using this CSR from machine mode to deactivate counters should consider
the tradeoffs in the context of the overall system requirements before using the register.
Additional logic may also be required, such as authentication of lower-privilege clients
that have access to the corresponding `scountinhibit` CSR. The `mcounteren` CSR controls
which counters can be directly accessed by lower-privilege modes.

The designer should also be aware that the cycle counter may be shared between harts. In
such implementations, configuring `mcountinhibit.CY` to control the cycle count on one
hart propagates the configuration to all harts sharing the counter.

[#sec:pmc:recom:newext]
#### New extensions

The standard Hardware Performance Monitoring facility and extensions defined
by the RISC-V specifications, as described in the previous section, provide an
important foundation for implementing safety-related hardware performance counters.

Working groups within the RISC-V International *Performance Analysis* Special
Interest Group are developing new extensions intended to enable more efficient
implementations of functional safety mechanisms based on performance counters.

New processor implementations targeting safety-critical domains should consider
integrating these extensions where appropriate.

Examples of such work include:

* An extension providing standardized naming and definitions for the most common
performance events that can be found across different implementations.
* Performance event sampling extensions providing (1) precise attribution of the
instruction that caused a performance counter to overflow and (2) sampling of instructions
and/or uops, with collection of run-time metadata for each instruction/uop, including
data virtual addresses, selected event occurrences, and incurred latencies.
* A self-hosted trace extension providing debugger-like functionality that can be used by
the core itself and the software running on it without relying on an external debugger.

The former, standardized naming and definitions for performance events, is particularly
relevant to safety-critical domains because it allows functional safety software that
uses performance counters to be reused across different RISC-V processor implementations
with little or no modification.

This can also reduce the effort required for verification, validation, and certification
when developing safety-critical systems, since the software does not need to be modified
for each processor implementation. This benefit, of course, depends on the different
RISC-V processor implementations conforming to the extension.

The latter extensions, performance event sampling and self-hosted trace, open opportunities
for new functional safety mechanisms and/or more efficient implementations of existing ones.

Processors implementing these extensions should consider providing dedicated resources,
including memory and paths to access that memory, for storing the generated samples and traces.
If these resources are shared with the rest of the system, applications may experience
interference; see xref:sec:partitioning.

[#sec:pmc:recom:socpmc]
#### SoC-level counters

The RISC-V specifications provide performance counters for hart-related events.
However, safety-critical systems, particularly those using complex SoCs (e.g.,
multicore systems), require observation of events outside the harts, especially
for resources shared among multiple harts, such as buses and shared memory structures.

Processors for safety-critical systems should consider implementing dedicated
SoC-level performance counters.

[#sec:pmc:activities]
### Relevant activities

#### Related external bodies

Performance counters typically have very diverse specifications on different
processors (Power, x86, ...).

Linux features the `perf` command for accessing and instrumenting performance counters.
Other operating systems and processor vendors provide similar tools.

#### Related chapters

(QoS) policies or even to dynamically influence them. Refer to xref:sec:qos[xrefstyle=full].
